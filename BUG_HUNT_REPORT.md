### 4. [HIGH] PUSHn at end of code with missing immediate bytes aborts with InvalidPush instead of zero-padding
- **Location:** `instructions/handlers_stack.zig:36` (confidence: high)
- **Problem:** When a PUSH instruction appears at the end of bytecode with fewer immediate data bytes than its operand width (e.g. code = [0x61, 0x12] meaning PUSH2 with only one data byte, or a bare trailing 0x60), the EVM specification reads the immediate via a zero-padding buffer read: the missing trailing bytes are treated as 0x00 and the (zero-extended) value is pushed onto the stack, after which the PC advances past the end of code and execution halts normally (the surrounding call succeeds). This implementation instead calls frame.readImmediate(push_size), which returns null whenever pc+1+size exceeds code.len, and then returns error.InvalidPush. That error propagates up and fails the entire call/transaction frame rather than completing successfully with a zero-padded push. This diverges from the execution-spec push_n behavior (data = buffer_read(evm.code, evm.pc+1, num_bytes), where buffer_read pads with zeros past the end) and from geth (RightPadBytes). Real bytecode (and consensus tests such as the classic push-at-end-of-code cases) relies on this padding semantics, so contracts ending in a truncated PUSH that should succeed will incorrectly fail here. The unit test handlers_stack_test.zig:301 codifies the wrong behavior by asserting error.InvalidPush for PUSH2 with one data byte.
- **Fix:** Make readImmediate (bytecode.zig) zero-pad instead of returning null: read min(size, code.len - (pc+1)) available bytes into the low bytes of the result and treat all missing trailing bytes as 0 (equivalent to result <<= 8*missing). Then push() always succeeds: push the zero-padded value, charge the normal PUSH gas, and set frame.pc += 1 + push_size (it will exceed code.len, terminating the loop). Update handlers_stack_test.zig:291-301 to assert the zero-padded value (e.g. PUSH2 0x12 pushes 0x1200) and success rather than error.InvalidPush.
- **Verifier:** Verified against actual code. handlers_stack.zig:36 does `const value = frame.readImmediate(push_size) orelse return error.InvalidPush;`. bytecode.zig:52-59 `readImmediate` returns null whenever `pc_usize + 1 + size_usize > self.code.len` (truncated trailing PUSH). PUSH opcodes 0x5f-0x7f are dispatched to StackHandlers.push at frame.zig:473, and the main loop (frame.zig:549-555) calls `try self.step()`, so error.InvalidPush propagates out and fails the entire frame/transaction — there is no catch that converts it to a normal halt. Bytecode.init (bytecode.zig:15-25) stores `code` as-is with no zero-padding, so the truncation path is real at runtime. This contradicts canonical EVM semantics for PUSHn: the execution-spec reads immediate data via buffer_read (evm.code, pc+1, num_bytes), which zero-pads bytes past the end of code and never raises, then advances pc past code end so execution halts normally with success; geth uses RightPadBytes equivalently. So `[0x61,0x12]` (PUSH2 with one data byte) must push 0x1200 and succeed, but this implementation errors. The test at handlers_stack_test.zig:291-301 codifies the incorrect behavior by asserting error.InvalidPush. (Note: the execution-specs submodule is not checked out / empty in this environment, so the Python reference could not be quoted directly, but the buffer_read/RightPadBytes zero-padding behavior for trailing truncated PUSH is canonical and unambiguous EVM behavior exercised by ethereum/tests.) Real correctness/consensus bug; kept at high rather than critical because it only affects the relatively uncommon trailing-truncated-PUSH case.

### 8. [MEDIUM] BLOCKHASH: u256 overflow panic on large block-number operand
- **Location:** `instructions/handlers_block.zig:29` (confidence: high)
- **Problem:** The BLOCKHASH handler pops a stack operand into `block_number` (a u256, since `frame.popStack()` returns u256) and then unconditionally computes `const max_block_number = block_number + 256;` on its own line, BEFORE any range check. - **Fix:** Rewrite the range test to avoid additive overflow, e.g. compare without forming `block_number + 256`: `if (block_number >= current_block) { push 0 } else { const delta = current_block - block_number; if (delta > 256) { push 0 } else { ... } }`. Since `block_number < current_block` (a u64) in the else-branch, `current_block - block_number` is safe and small. Do not compute `block_number + 256` on a full-width u256 operand.
- **Verifier:** Confirmed by reading /Users/williamcory/chop/lib/guillotine-mini/src/instructions/handlers_block.zig:22-30 and frame.zig:171. `block_number` is a u256 (frame.popStack() returns EvmError!u256). The correct EVM/spec behavior for any out-of-range (including huge) block-number operand is to push 0 (Python block_hash uses arbitrary-precision ints that never overflow and returns Hash32 of zero for block_number >= current_block_number). The `or` short-circuit in the `if` on line 30 cannot prevent the crash because the overflowing addition is already evaluated on the preceding line 29. In ReleaseFast/ReleaseSmall builds it would silently wrap instead of crashing, yielding an incorrect max_block_number and thus a wrong comparison result — still a correctness bug. The suggested fix (compare via subtraction in the branch where block_number < current_block, a u64) is sound and avoids the overflow. Note: the execution-specs submodule is not checked out in this clone, but the BLOCKHASH spec semantics (return 0 for out-of-range) are unambiguous and the bug is provable purely from the Zig code and Zig's overflow semantics.
