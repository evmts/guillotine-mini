# 2. State, Storage & Snapshots

Imagine you write a test to verify that Alice has 10 ETH before calling a contract:

```zig
try vm.balances.put(alice, 10_000_000_000_000_000_000);
_ = vm.call(.{ .call = .{
    .caller = alice,
    .to = contract,
    .value = 0,
    .input = &.{},
    .gas = 100_000,
} });
std.debug.print("Alice balance: {d}\n", .{vm.get_balance(alice)});
```

You run it, expecting `10000000000000000000`. Instead, it prints:

```text
Alice balance: 0
```

**Wait — what just happened?!** Where did Alice's 10 ETH go?!

## The `initTransactionState()` mystery solved

Open `src/evm.zig` lines 714–719 and the puzzle clicks immediately:

```zig
const bytecode = if (params.isCreate()) &[_]u8{} else self.get_code(address);
...
self.initTransactionState(blob_versioned_hashes) catch ...
```

Inside `initTransactionState()` (lines 227–231):

```zig
self.storage = Storage.init(arena_allocator, self.host, self.pending_storage_injector);
self.balances.clearRetainingCapacity();
self.nonces.clearRetainingCapacity();
self.code.clearRetainingCapacity();
```

`vm.call()` starts every transaction with a clean slate for its internal maps! The **only** pre-seeded map entry that survives is `vm.code.get(target)`, because `call()` reads `self.get_code(address)` five lines *before* resetting the maps.

<WatchOut title="Internal maps vs HostInterface">
With `host = null`:
- `vm.code.put(target, code)` works for a single contract because `call()` reads it before `initTransactionState()`.
- Pre-seeding `vm.balances`, `vm.nonces`, or a *second* contract in `vm.code` gets wiped at the start of `vm.call()`.
- Touching `vm.storage` before calling `vm.call()` or `vm.initTransactionState()` panics (`vm.storage` starts `undefined`).

Whenever you need pre-funded accounts, pre-existing storage, or Contract A calling Contract B, pass a [`HostInterface`](/tutorials/custom-host). `initTransactionState()` never clears your host.
</WatchOut>

## Three storage maps, one revert model

Once a transaction is running, `src/storage.zig` keeps **three** distinct maps. Each exists for a specific Ethereum rule:

<StateSnapshotDiagram />

1. **`storage` (persistent):** Holds the live slot values modified by `SSTORE`. Restored on frame revert; survives when a transaction commits (if backed by a host, writes pass through to `host.setStorage()`).
2. **`original_storage`:** Records each slot's value at the start of the transaction on first write. Never overwritten mid-transaction — `SSTORE` needs `(original, current, new)` to compute EIP-2200 / EIP-3529 gas costs and refunds accurately.
3. **`transient` (EIP-1153, Cancun+):** Driven by `TLOAD` (`0x5c`) and `TSTORE` (`0x5d`). Always costs **100 gas** (never cold), **does revert** if the frame reverts, and is wiped unconditionally at the end of the transaction.

<MentalModel title="Warm sets are per-transaction, and they revert too">
At transaction start (`preWarmTransaction`), the EVM pre-warms:
- `tx.origin` and the call target `to`
- `block.coinbase` (Shanghai+, EIP-3651)
- Active precompiles: `0x01`–`0x09` (Berlin), `0x01`–`0x0A` (Cancun), `0x01`–`0x13` (Prague), plus `0x0100` `P256VERIFY` (Osaka)
- Any addresses and storage slots supplied via `vm.setAccessList(...)` (EIP-2930)

If a nested call warms a new address or storage slot and then **reverts**, `AccessListManager.restore()` makes that address or slot **cold again** for the parent frame!
</MentalModel>

## Reading storage and refunds after a call

Let's execute a contract that writes `42` to slot `0`, reads it back, and clears it to `0` — then inspect `vm.storage` and `result.refund_counter`:

```zig
const bytecode = [_]u8{
    // SSTORE(slot=0, value=42) -> 20,000 + 2,100 cold = 22,100 gas
    0x60, 0x2a, // PUSH1 42
    0x60, 0x00, // PUSH1 0
    0x55,       // SSTORE

    // SLOAD(slot=0) -> warm! 100 gas
    0x60, 0x00, // PUSH1 0
    0x54,       // SLOAD

    // Return the loaded value
    0x60, 0x00, // PUSH1 0
    0x52,       // MSTORE
    0x60, 0x20, // PUSH1 32
    0x60, 0x00, // PUSH1 0
    0xf3,       // RETURN
};
try vm.code.put(target, &bytecode);

const result = vm.call(.{ .call = .{
    .caller = voltaire.ZERO_ADDRESS,
    .to = target,
    .value = 0,
    .input = &.{},
    .gas = 100_000,
} });

const stored = try vm.storage.get(target, 0); // 42
```

Notice that `vm.storage` stays readable *after* `vm.call()` returns (only `transient` storage and warm sets are cleared at end-of-tx), right up until the next `vm.call()` or `vm.deinit()`.

## Snapshotting setters (for code running inside a frame)

If you write custom opcode handlers or precompiles that modify balances, nonces, or code mid-execution, never mutate `vm.balances` directly — use the copy-on-write helpers so nested reverts undo your write cleanly:

```zig
try vm.setBalanceWithSnapshot(addr, new_balance);
try vm.setNonceWithSnapshot(addr, new_nonce);
try vm.setCodeWithSnapshot(addr, new_code);
```

Each helper records the pre-write value into **every** active snapshot on `balance_snapshot_stack` / `nonce_snapshot_stack` / `code_snapshot_stack` before applying the update.
